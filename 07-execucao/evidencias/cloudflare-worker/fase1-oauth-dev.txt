=== 5) `POST /mcp/auth` (protegido) sem bearer token ===

HTTP/1.1 401 Unauthorized
WWW-Authenticate: Bearer realm="OAuth", resource_metadata="http://localhost:18787/.well-known/oauth-protected-resource/mcp/auth", scope="mcp:read"
Cache-Control: no-store

Challenge correto: nomeia o resource_metadata certo e o scope mínimo (mcp:read), conforme MCP
authorization 2026-07-28 / RFC 6750.

=== 6) `GET /authorize` SEM identidade Cloudflare Access (config wrangler.noaccess.jsonc, sem o
bloco access.dev) — deve falhar fechado ===

HTTP/1.1 401 Unauthorized
Content-Type: text/plain; charset=utf-8

Cloudflare Access não confirmou a identidade desta requisição: nem ctx.access nem o header
Cf-Access-Jwt-Assertion estavam presentes — /authorize provavelmente ainda não está protegido por
uma Cloudflare Access application. Configure a Access application que protege /authorize (Zero
Trust → Access → Applications, ou Workers & Pages → este Worker → aba Access) e, se usar o fallback
manual, os secrets CF_ACCESS_TEAM_DOMAIN/CF_ACCESS_AUD (`wrangler secret put`) — ver D15 e
cloudflare-worker/README.md.

Confirma: requireAccessIdentity() falha fechado (não assume anônimo, não inventa identidade — I-02)
quando o Access real ainda não está configurado.

=== 7) `GET /authorize` COM identidade Cloudflare Access simulada (wrangler.jsonc access.dev:
aud="maestro-mcp-remote-dev", identity.email="dev@example.invalid") ===

HTTP/1.1 400 Bad Request
Content-Type: text/plain; charset=utf-8

client_id is required

Este é o erro CORRETO e ESPERADO neste ponto: nenhum client OAuth real está registrado ainda (sem
CIMD/DCR configurado do lado do cliente), e a requisição de teste não incluiu client_id/redirect_uri.
O fato de a resposta ser "client_id is required" (validação de parâmetros da própria biblioteca, via
oauth.parseAuthRequest()) — e NÃO o erro AccessNotConfiguredError do passo 6 — confirma que
requireAccessIdentity() passou com sucesso: a identidade simulada por access.dev foi lida via
ctx.access.getIdentity() e a execução chegou à etapa seguinte do fluxo.

=== Conclusão ===

Mecânica OAuth 2.1 + CIMD + identidade via Cloudflare Access verificada ponta a ponta no nível de
protocolo (discovery, challenge 401, fail-closed sem identidade, passagem com identidade simulada).
NÃO exercitado: o fluxo completo com um cliente OAuth real (CIMD de verdade ou client pré-registrado)
e consentimento até emissão de token — isso depende de (a) a Access application real configurada no
dashboard (D15, ainda pendente do usuário) e (b) um cliente MCP real tentando conectar. Rota pública
/mcp (mcp-server:remote, DE-012) confirmada sem mudança de comportamento.
